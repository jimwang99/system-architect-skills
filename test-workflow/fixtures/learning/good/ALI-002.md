# ALI-002: Database migration rollback failure
Date: 2026-07-26
Phase: debugging
Status: approved

**What happened:** A schema migration ran successfully on staging but failed on production, requiring a manual rollback that took three hours.

## L1: Environment parity assumption
- **What we assumed:** Staging and production databases had identical schema versions.
- **What is actually true:** Production had a backfill column added manually six months ago that was never tracked.
- **Evidence:** Migration log: `ERROR: column "legacy_flag" of relation "users" already exists`.
- **Why the assumption was wrong:** No automated schema drift detection between environments.
- **Class of error:** Environment configuration mismatch
- **Improvement items:**
  - **P0 — CI pipeline:** `infra/ci/schema-check.yml` — add schema drift comparison step before migration.
  - **P1 — Runbook:** `docs/runbooks/migration.md` — add pre-migration environment diff checklist.

## L2: Rollback procedure was untested
- **What we assumed:** The down-migration script would reverse all changes cleanly.
- **What is actually true:** The down script did not account for rows inserted during the failed migration window.
- **Evidence:** Post-rollback row count mismatch: 42 orphaned rows in `user_settings` table.
- **Why the assumption was wrong:** Down migrations were never exercised in integration tests.
- **Class of error:** Untested recovery path
- **Improvement items:**
  - **P0 — Test suite:** `tests/db/test_migrations.py` — add round-trip up/down migration test with data fixture.
  - **P2 — AI agent skill:** `skills/database-migration/SKILL.md` — mandate rollback dry-run before applying.

## L3: Alert threshold too coarse
- **What we assumed:** The existing error-rate alert would fire within two minutes of a bad deploy.
- **What is actually true:** The alert fired after eleven minutes because the threshold was set for sustained 5% error rate, not spike detection.
- **Evidence:** PagerDuty incident timeline shows alert at T+11m; first user report at T+3m.
- **Why the assumption was wrong:** Alert tuning had not been revisited since the service traffic doubled.
- **Class of error:** Monitoring gap
- **Improvement items:**
  - **P1 — Alert config:** `infra/alerts/api-errors.yaml` — lower spike threshold to 1% over 60-second window.
